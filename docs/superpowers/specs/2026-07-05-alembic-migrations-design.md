# Alembic Migrations — Design Spec

**Date:** 2026-07-05
**Status:** Approved (design)
**Scope:** Introduce Alembic as the versioned-migration mechanism for the Postgres schema, replacing
`create_all` **in production**. Increment **#4** of persistence-completion.

---

## 1. Motivation

`init_db` calls `Base.metadata.create_all`, which cannot evolve an existing schema — proven twice
during PR #19/#20, where the live dev DB had to be manually `drop_all`/`create_all`'d after a model
change. Every subsequent increment (#2b per-user state, #3 Chroma linkage) adds tables/columns, so a
real migration path is needed now, before that churn — so those increments ship migration-clean.

## 2. Design decisions

| Decision | Choice |
|---|---|
| Baseline migration body | `Base.metadata.create_all(bind)` / `drop_all(bind)` — the baseline always matches the models (zero drift, no autogenerate/JSONB-variant rendering quirks) and stamps `alembic_version`. Future increments author explicit delta migrations on top. |
| Test schema path | Keep `init_db`/`create_all` for the offline SQLite suite — fast, and **alembic-free** so the bare-`python3.11` invariant holds (alembic is an `infra` extra, not installed on the system interpreter). |
| Production schema path | `alembic upgrade head` (documented); `build_app_state` is left on `init_db` this increment (switching it would pull alembic into the API import path — deferred, non-goal). |
| Model/migration lockstep | A parity test (`importorskip("alembic")`) runs `upgrade head` on a temp SQLite DB and asserts the resulting tables equal `Base.metadata.tables` + `alembic_version`. |
| DB URL source | `migrations/env.py` reads `NOVA_DATABASE_URL` from the environment, falling back to the `alembic.ini` value; `target_metadata = Base.metadata`. |

## 3. Components

### 3.1 Dependency
`pyproject.toml`: add `alembic>=1.13` to the `infra` optional-dependencies extra (so `dev`/`infra`
installs get it; the base/bare interpreter does not).

### 3.2 Alembic scaffold
- `alembic.ini` (repo root): `script_location = migrations`; a default `sqlalchemy.url` (dev Postgres)
  that `env.py` overrides from the environment.
- `migrations/env.py`: imports `infra.db.models` (registers all tables), sets
  `target_metadata = Base.metadata`, resolves the URL from `NOVA_DATABASE_URL` (env) else the ini,
  and implements the standard offline (`run_migrations_offline`) and online (`run_migrations_online`)
  runners with `render_as_batch=True` (SQLite-friendly for future ALTERs).
- `migrations/script.py.mako`: the standard revision template.

### 3.3 Baseline migration
`migrations/versions/0001_baseline_schema.py` (`revision = "0001_baseline"`, `down_revision = None`):
- `upgrade()`: `from infra.db.base import Base; import infra.db.models; Base.metadata.create_all(op.get_bind())`
- `downgrade()`: `Base.metadata.drop_all(op.get_bind())`

### 3.4 Docs
`CLAUDE.md` Infrastructure/DB note: production/dev-persistent schema is managed by
`alembic upgrade head`; `init_db` (`create_all`) remains the fast path for the offline test suite and
ad-hoc bootstrap. Add the command to the Commands section.

## 4. Testing

- `tests/integration_infra/test_migrations.py` (`importorskip("alembic")`, **not** `@pytest.mark.docker`
  — runs on a temp-file SQLite so it executes in the venv without a container):
  - Build an Alembic `Config` pointing at `migrations/`, override `sqlalchemy.url` to a
    `tmp_path` SQLite file, `command.upgrade(cfg, "head")`.
  - Assert `set(inspect(engine).get_table_names()) >= set(Base.metadata.tables)` and that
    `alembic_version` exists.
  - `command.downgrade(cfg, "base")` then assert the domain tables are gone (migration is reversible).
- **Invariant:** bare `python3.11` suite stays green — the migration test skips (no alembic), and no
  production code imports alembic.

## 5. Success criteria
1. `alembic upgrade head` builds the full 16-table schema (+ `alembic_version`) from empty.
2. The parity test proves the baseline matches `Base.metadata`; downgrade is clean.
3. Offline suite green on bare `python3.11` (alembic test skips); venv runs it.
4. No production import of alembic; `init_db` still serves tests.

## 6. Non-goals
Switching `build_app_state` to run migrations at startup · autogenerated per-model DDL in the baseline ·
data migrations · multi-head/branching workflows · a `scripts/` migration wrapper (the `alembic`
command suffices).
